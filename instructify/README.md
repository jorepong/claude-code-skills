# instructify

**AI에게 줄 지침·프롬프트를, "무엇을 하라"가 아니라 "왜 그렇게 해야 하는가(의도)"로 쓰게 만드는 스킬.**

## 어떤 문제를 푸는가

AI에게 지침을 쓸 때 흔히 하는 실수는 **동작을 하나하나 못박는 것**입니다. "A 상황엔 이렇게, B 상황엔 이렇게" 식으로 케이스를 나열하면, 그 AI는 적힌 케이스는 잘 처리하지만 **처음 보는 상황에서는 무너집니다.** 적어둔 예시나 대사가 오히려 응답을 그쪽으로 끌어당겨, 유연성을 죽입니다.

instructify는 이 문제를 뒤집습니다. 지침을 받아, **그 지침을 읽고 동작할 LLM이 의도대로 움직이게** 다시 씁니다. 대상은 시스템 프롬프트, `CLAUDE.md`, 다른 스킬의 `SKILL.md`, 에이전트 규칙, 일반 프롬프트까지 — LLM의 행동을 규정하는 모든 글입니다.

## 어떻게 동작하는가

두 가지가 이 스킬의 본질이고, 나머지는 AI의 자율 판단에 맡깁니다.

1. **의도 파악이 작성에 선행한다.** 사용자의 말을 기계적으로 명령문으로 옮기지 않습니다. 먼저 *왜* 이 지침을 원하는지 — 어떤 행동을 만들고 싶고 어떤 실패를 막으려는지 — 를 이해하고, 그 의도를 지침에 담습니다. 그래야 지침을 따르는 LLM이 처음 보는 상황에서도 "이 지침이 지키려던 게 무엇인가"로 되짚어 스스로 판단합니다.

2. **유연성을 죽이지 않는다.** 지침은 응답을 좁히는 도구가 아니라, **방향은 맞추되 합성은 LLM에 맡기는** 도구입니다.

이 관점에서 핵심 판단이 하나 나옵니다 — **계약 vs 행동 공간의 구분:**

- **계약** (변형이 곧 버그인 영역): 출력 스키마, 파일 수정 규칙, 명명 규약, 보안 경계, 규칙 간 우선순위. → 절차적으로 못박습니다.
- **행동 공간** (창의·판단·맥락 적응이 가치인 영역): → 의도만 주고 나머지는 명시적으로 위임합니다.

즉 "절차를 쓰지 마라"가 아니라 **"절차를 의도에 종속시켜라"**가 기준입니다.

## 쓰는 법

```
/instructify [지침화할 내용 또는 개선할 기존 지침]
```

- "이 규칙들 지침으로 만들어줘" → 소재를 읽고 의도를 파악해 지침을 새로 씁니다.
- "이 시스템 프롬프트 개선해줘" → 지배적 예시·이중 명세·죽은 유연성을 찾아 의도 기반으로 고칩니다.

작성 후에는 파악한 **사용자 의도**를 먼저 밝히고(해석이 맞는지 확인할 수 있게), 어디를 의도로 남기고 어디를 절차로 못박았는지 그 근거를 덧붙입니다.

## 폴더 구성

- `SKILL.md` — 진입 지침(불변량, 동작 순서, 자기 점검용 '막다른 신호').
- `references/principles.md` — 왜 이 방식이 LLM에서 작동하는지, 각 원칙의 깊은 근거.
