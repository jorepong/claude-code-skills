# 시각 자료 (Visual assets) — 상세 지침

이 문서는 SKILL.md의 "시각 자료" 원칙을 실제로 어떻게 구현하는지 — 언제 넣을지 판단하는 기준, 형태 선택, 본문 마커 형식, 파일 배치, png 렌더링 방법 — 을 구체적으로 정한다. 시각 자료를 하나라도 넣기로 했다면 이 문서를 따른다.

## 1. 넣을지 말지 — 절제의 기준

시각 자료는 독자의 이해를 크게 높이지만, 남발하면 오히려 집중과 이해를 떨어뜨린다. 그래서 **개수를 늘리는 방향이 아니라, 꼭 필요한 자리에만 넣는 방향**으로 판단한다.

각 시각 자료는 넣기 전에 이 테스트를 통과해야 한다:

> **이 시각 자료가 없으면, 독자가 이해에서 실제로 손해를 보는가?**

- 통과: 텍스트만으로는 관계·흐름·구조·전후 대조가 머릿속에 잘 그려지지 않아, 그림이 있어야 독자가 정확히 이해하는 경우.
- 탈락: 본문을 한 번 더 그림으로 반복하는 장식, 분량을 채우려는 것, "있으면 좋아 보여서" 넣는 것. 이런 건 넣지 않는다.

판단이 서지 않으면 **넣지 않는 쪽**을 택한다. 글 한 편에 시각 자료가 없어도 되고, 정말 필요하면 여러 개가 있어도 된다. 개수에 정답은 없고, 매 자료가 위 테스트를 통과했는지만 본다.

시각 자료가 특히 값어치를 하는 전형적 자리:
- **구조·아키텍처**: 컴포넌트가 어떻게 연결되는지 (→ svg 도식 또는 mermaid flowchart/graph).
- **흐름·순서**: 요청/데이터가 시간·단계를 따라 흐르는 과정 (→ mermaid flowchart, sequenceDiagram).
- **상태 전이**: 상태가 조건에 따라 바뀌는 관계 (→ mermaid stateDiagram).
- **비교·대응**: 여러 항목을 속성별로 나란히 놓기 (→ 표).
- **전후 대조(before/after)**: 바뀌기 전과 후를 나란히 (→ 표 또는 svg 2단 구성).
- **수치 추이·분포**: 값의 변화나 분포 (→ svg 차트).

## 2. 형태 선택 — 제한 없음

소재를 가장 잘 전달하는 형태를 고른다. 정해진 형태는 없다.

| 형태 | 언제 | 본문 처리 | png 준비 |
|---|---|---|---|
| **표(마크다운 table)** | 항목·속성 비교, 대응 관계, 전후 대조처럼 텍스트로 완결되는 것 | 본문에 마크다운 표를 **직접** 쓴다 | png 불필요 (텍스트가 그 자체로 최종 형태) |
| **mermaid** | 흐름·순서·구조·관계·상태 전이 등 다이어그램으로 표준화되는 것 | 자리 표시 마커(§3) | png 준비 (§4) |
| **svg** | 위 어느 것으로도 안 되는 커스텀 도식·레이아웃·차트 | 자리 표시 마커(§3) | png 준비 (§4) |
| **그 외** | 소재가 요구하는 어떤 형태든 | 자리 표시 마커(§3) | png 준비 (§4) |

**표는 예외다.** 표는 마크다운 텍스트 자체가 최종 결과물이라 편집·복사·접근성 면에서 png보다 낫다. 그러니 표는 본문에 직접 쓰고 png로 만들지 않는다. 표를 굳이 이미지로 만들어야 할 특별한 이유(예: 셀 병합·색상 강조가 표현의 핵심)가 있을 때만 svg로 그려 png로 준비한다.

**mermaid·svg 등 렌더링이 필요한 형태**는 본문에 자리 표시를 남기고, 실제 이미지를 png로 준비한다.

## 3. 본문 자리 표시 (마커)

렌더링형 시각 자료(mermaid·svg 등)가 들어갈 자리에는, **글을 쓰는 사람(작성자)이 "여기에 무슨 그림이 들어가는지" 바로 파악할 수 있는 표시**를 남긴다. 표준 마크다운 이미지 임베드를 쓰되, 캡션이 그 자리의 설명이 되게 한다.

형식:

```markdown
![그림 1. 요청이 토큰 버킷을 통과하는 흐름 — 버킷이 비면 요청은 대기열로 빠진다.](assets/2026-07-05-token-bucket/fig-1.png)
```

- `그림 N.`으로 번호를 매겨 본문에서 "그림 1에서 보듯" 식으로 참조할 수 있게 한다.
- 캡션(alt 텍스트)은 **무엇을 보여주는 그림인지 한 문장**으로 쓴다. 이미지가 로드되지 않아도 이 문장만으로 자리와 내용이 파악되어야 한다.
- 경로는 포스트 파일 기준 상대경로(§5)로 쓴다.

캡션을 그림 아래에 눈에 보이게 두고 싶으면, 임베드 다음 줄에 이탤릭 캡션을 덧붙여도 된다:

```markdown
![그림 1](assets/2026-07-05-token-bucket/fig-1.png)

*그림 1. 요청이 토큰 버킷을 통과하는 흐름 — 버킷이 비면 요청은 대기열로 빠진다.*
```

## 4. png 렌더링

각 렌더링형 시각 자료를 png 파일로 만들어 포스트와 함께 저장한다. **png와 함께 그 소스(svg 파일 또는 mermaid `.mmd`)도 남긴다** — 나중에 작성자가 수정·재생성할 수 있어야 하기 때문이다.

렌더링은 환경에 있는 도구로 한다. 아래 순서로 시도한다.

### 4-1. svg → png (가장 확실한 경로: headless Chrome)

svg는 AI가 코드로 직접 작성할 수 있어 통제력이 높고, 별도 다이어그램 도구 없이 headless 브라우저만으로 png가 된다. macOS에 Google Chrome이 있으면 이 경로가 가장 안정적이다.

```bash
# svg 파일을 만든 뒤:
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu \
  --force-device-scale-factor=2 \
  --default-background-color=00000000 \
  --screenshot="/abs/path/fig-1.png" \
  --window-size=<svg width>,<svg height> \
  "/abs/path/fig-1.svg"
```

- `--force-device-scale-factor=2` : 2배 해상도로 캡처해 레티나에서도 또렷하게(파일의 픽셀 크기가 2배가 된다).
- `--default-background-color=00000000` : 투명 배경. 흰 배경을 원하면 이 옵션을 빼거나 svg에 배경 `<rect>`를 넣는다.
- `--window-size` 는 svg의 `width`/`height`(px)와 맞춘다. viewBox만 있고 width/height가 없으면 svg에 명시적으로 넣는다.
- 경로는 **절대경로**로 준다(headless Chrome은 상대경로·`~`를 신뢰하기 어렵다).
- 다른 OS: Chrome/Chromium 실행 파일 경로만 바꾸면 동일하게 동작한다. `chromium`, `google-chrome` 등.

### 4-2. mermaid → png

두 경로가 있다. 우선순위대로 시도한다.

**(a) mermaid-cli (mmdc)** — 표준 경로. 전역 설치가 없으면 npx로 실행한다.

```bash
npx -y @mermaid-js/mermaid-cli -i fig-2.mmd -o fig-2.png -s 2 -b transparent
```

- `-s 2` : 2배 스케일. `-b transparent` : 투명 배경.
- **주의**: 첫 실행 시 puppeteer가 Chromium(수백 MB)을 내려받아 오래 걸릴 수 있다. 시간이 걸려도 정상이다.

**(b) 폴백 — mermaid를 svg로 렌더한 뒤 4-1로 png화**하거나, 다이어그램을 직접 svg로 그린다. mermaid-cli가 환경에서 동작하지 않으면 이 폴백을 쓴다.

### 4-3. 표(예외적으로 이미지화가 필요할 때) → png

표는 원칙적으로 본문 마크다운으로 끝낸다(§2). 이미지가 꼭 필요하면 표를 svg(또는 간단한 HTML 파일)로 만들어 4-1의 headless Chrome 경로로 png화한다.

### 4-4. 렌더링 도구가 없을 때 (폴백)

png를 만들 도구가 환경에 하나도 없으면:

1. **소스는 반드시 남긴다** — svg 파일과 mermaid `.mmd` 파일은 그대로 저장한다.
2. 본문 마커는 그대로 두되, **어떤 시각 자료가 png로 렌더되지 못했는지** 최종 보고에서 사용자에게 분명히 알린다(예: "fig-2는 mermaid 소스만 준비됨. `mmdc` 또는 Chrome 설치 후 렌더 필요").
3. 없는 png를 있는 것처럼 보고하지 않는다.

## 5. 파일 배치

포스트 하나에 딸린 시각 자료는 그 포스트 전용 하위 폴더에 모은다.

```
docs/posts/
  2026-07-05-token-bucket.md
  assets/
    2026-07-05-token-bucket/
      fig-1.png        # 렌더된 이미지
      fig-1.svg        # 소스
      fig-2.png
      fig-2.mmd        # mermaid 소스
```

- 에셋 폴더명은 포스트 파일명(확장자 제외)과 같게: `assets/{포스트-slug}/`.
- 파일명은 `fig-1`, `fig-2` … 로 본문 그림 번호와 일치시킨다.
- 본문에서의 참조 경로는 포스트 파일 기준 상대경로: `assets/2026-07-05-token-bucket/fig-1.png`.

## 6. 최종 보고에 포함할 것

포스트를 제시할 때, 시각 자료가 있으면 다음을 함께 밝힌다:
- 각 포스트에 시각 자료를 **몇 개, 어떤 형태로** 넣었는지.
- png가 실제로 렌더되었는지, 아니면 소스만 준비되어 별도 렌더가 필요한지(§4-4).
