# 시각 자료 작법 — 학습 역할에 맞는 매체를 고르고 읽히게 만든다

**언제·어디에** 시각을 넣는가는 `explanation-principles.md`의 '처음 배우는 개념은 시각과 함께 가르친다'가 정한다. 이 문서는 그 다음 — 학습 역할에 맞는 매체를 고르고 정적 다이어그램을 읽히게 그리는 작법이다.

매체는 역할로 가른다. 학습자가 입력·조건을 바꾸며 결과의 인과를 비교해야 하면 `simulation.md`의 인터랙티브 시뮬레이션, 정해진 시간·변화·과정을 관찰하면 `animation.md`의 Remotion 애니메이션, 수량의 패턴·함수·분포·추세는 Vega-Lite 선언형 차트, 움직임 없는 구조·관계는 Mermaid·SVG, 수식 자체가 사고의 중심이면 KaTeX를 쓴다. “동적이면 모두 영상”으로 뭉뚱그리지 않는다.

시각의 역할은 새로운 정보를 추가하는 데 한정되지 않는다. 본문에서 이미 설명한 개념을 읽는 동안 함께 보여 주어 정신 모형을 유지시키는 **동반 시각**도 적극적으로 만든다. 이때는 본문과 정보가 겹쳐도 괜찮다. 텍스트의 순차적 설명을 공간적으로 동시에 보이게 하거나, 생소한 구성 요소에 눈으로 붙잡을 형태를 주는 것 자체가 학습 역할이다.

## 시각 커버리지 하한

`learn`의 무겁게 모드는 다음 운영 기준을 적용한다. 이는 글과 그림의 면적 비율이 아니라 시각화 가능한 학습 단위의 커버리지 기준이다.

- 시간 변화·상태 전이·이동·알고리즘 실행·프로토콜 왕복은 모두 애니메이션으로 만든다. 학습자가 조건을 바꿔야 하면 애니메이션 대신 시뮬레이션으로 만든다.
- 구조·공간 배치·구성 요소 관계·데이터 흐름은 모두 다이어그램이나 주석 이미지로 만든다.
- 입력에 따른 결과 변화·수량 패턴·트레이드오프 곡선은 모두 시뮬레이션이나 차트로 만든다.
- 처음 등장하는 실체·정신 모형·실제 작동 장면·정상/실패 예제·경계 사례도 가능한 대부분에 동반 시각을 둔다.
- 각 주요 H2에는 그래픽 시각 앵커가 하나 이상 있는 것을 기본으로 한다. 시각이 없는 H2는 짧은 전환, 순수 언어적 정의·논증, 시각이 오해를 만드는 경우로 제한한다.
- 주요 H2가 4개 이상인 심층 문서는 보통 그래픽 시각 자료 3~6개 이상을 갖춘다. 약 1,500~2,500단어 문서의 대표 그림 하나는 부족 신호다. 기회가 많으면 6개를 넘어도 된다.
- 그래픽 시각 앵커에는 Mermaid·SVG·래스터 삽화·주석 이미지·Vega-Lite 차트·Remotion 애니메이션·시뮬레이션이 포함된다. 코드·KaTeX 수식·일반 표·콜아웃은 이것을 대체하지 않는다.

시각 수를 늘릴 때 본문을 줄이지 않는다. 시각은 완성된 설명 위에 얹는 별도 학습 경로다.

**플레이어 전제.** 산출물은 `player.html`(Mermaid 11·KaTeX 0.18·Vega-Lite 5, 밝은 종이 팔레트)로 렌더된다.

- 문법이 깨진 Mermaid는 그림 대신 **경고 카드 + 원본 코드**로 표시된다 — 학습자에게 그대로 노출되는 파손이므로, 아래 '문법 함정' 규칙으로 처음부터 깨지지 않게 쓴다.
- 렌더된 다이어그램에는 확대·크게 보기 컨트롤이 자동으로 붙는다. 그러나 이것은 세부를 들여다보는 보조 수단이지, 과밀한 다이어그램의 면죄부가 아니다 — 아래 노드 상한은 지킨다.

## 1. 무엇을 보여 주려는가 → 타입 선택

내용에 맞는 Mermaid 타입을 고른다. 이 선택이 절반이다 — 흐름을 시퀀스로, 상태를 흐름도로 그리면 아무리 잘 그려도 어색하다.

| 보여 주려는 것 | 타입 | 선언 |
|---|---|---|
| 처리 흐름·결정 분기·파이프라인 | 흐름도 | `flowchart TD` (또는 `graph TD`) |
| 요청/응답·시간 순서의 상호작용(API 호출, 프로토콜 왕복) | 시퀀스 | `sequenceDiagram` |
| 상태 전이·생애주기 | 상태도 | `stateDiagram-v2` (라벨 제약 주의 — 아래) |
| 테이블·엔티티 관계 | ER | `erDiagram` |
| 클래스·도메인 모델(속성·메서드) | 클래스 | `classDiagram` |
| 시스템 경계·컴포넌트 배치(아키텍처) | 흐름도 + `subgraph` | `graph TD` — 전용 `C4Context` 문법은 테마를 무시하므로 쓰지 않는다 |
| 계층적 분해·개념 지도 | 마인드맵 | `mindmap` |

**선수 관계·학습 순서는 마인드맵보다 방향 그래프가 우선이다.** `flowchart TD`에서 선행 개념을 위에, 그것이 여는 개념을 아래에 두고 화살표에 관계를 짧게 단다. 마인드맵은 계층적 분류에 쓰고, "A를 알아야 B를 이해한다" 같은 의존 관계에는 쓰지 않는다. 무겁게 모드의 `overview.md`에는 학습 순서를 결정하는 분기·합류가 있을 때 이 지도를 둔다.

비교·매트릭스는 다이어그램이 아니라 **마크다운 표**가 1순위다(`explanation-principles.md`). 3~4단계 단순 선형 흐름(A→B→C)도 순서·책임 경계·전후 차이를 눈으로 붙잡거나 읽는 동안 현재 위치를 유지하는 것이 학습 역할이라면 작은 Mermaid로 둔다. 본문과 정보가 같다는 이유만으로 생략하지 않고, 눈으로 함께 볼 때 얻는 역할까지 없을 때만 생략한다.

### 개념 삽화와 주석 이미지

생소한 대상의 외형·배치·장면·공간적 맥락을 함께 보며 읽는 것이 도움이 되면 다이어그램만 고집하지 않고 이미지 자료를 만든다. 예컨대 하드웨어 구성 요소의 위치, 물리 현상의 실제 단계, 생물학적 구조, 소프트웨어 구성 요소의 실제 데이터 이동, 화면에서 주목할 위치는 개념 삽화나 주석 이미지가 잘 맞는다. 시각 자료도 은유적 장면으로 실제 메커니즘을 대체하지 않고 구성 요소와 관계를 문자 그대로 보여 준다.

- 이미지 자체에 새로운 명제가 없어도 괜찮다. 본문이 순서대로 설명하는 대상을 한 화면에 유지해 읽기의 부담을 낮추면 목적을 달성한다.
- 본문 곳곳의 학습 순간에 배치한다. 문서 맨 위의 대표 이미지 하나로 모든 설명을 대신하지 않는다.
- 정확한 구조가 핵심이면 SVG·다이어그램을, 형태와 장면의 직관이 핵심이면 래스터 삽화를 쓴다. 기존 화면이나 사진에서 특정 위치를 봐야 하면 원본 위에 번호·선·강조 영역을 얹은 주석 이미지를 쓴다.
- 분위기만 맞는 스톡 이미지, 개념과 연결되지 않는 장식, 본문에서 무엇을 보아야 하는지 설명할 수 없는 이미지는 넣지 않는다.
- 대체 텍스트와 인접 문장에서 이 이미지를 왜 지금 보는지, 어디를 먼저 볼지를 짚는다.

## 2. 수식 — KaTeX

정의·증명·유도에서 기호 관계를 정확히 읽는 것이 학습 역할이면 KaTeX 수식을 쓴다. 플레이어는 다음 구분자를 렌더한다.

```markdown
문장 안에서는 \( E = mc^2 \)처럼 쓴다.

독립된 유도식은 다음처럼 쓴다.

\[
P(A \mid B) = \frac{P(B \mid A)P(A)}{P(B)}
\]
```

- 통화 기호와 충돌하는 단일 `$...$`는 쓰지 않는다. 인라인은 `\(...\)`, 블록은 `\[...\]` 또는 `$$...$$`를 쓴다.
- 수식만 던지지 않고 바로 앞뒤 문장에서 각 항과 변형의 이유를 말로 도출한다. KaTeX는 정확한 표기를 맡을 뿐 설명을 대신하지 않는다.
- 낭독 스크립트에서는 TeX 명령을 읽지 않는다. 같은 블록의 의미를 자연스러운 한국어 발음과 관계 설명으로 옮긴다.

## 3. 정량 시각 — Vega-Lite 선언형 차트

값의 크기·추세·분포·상관·전후 차이가 학습 내용이면 손 SVG 대신 `vega-lite` 코드 펜스에 JSON 명세를 쓴다. 플레이어가 Vega-Lite 차트로 승격하며, 라이브러리를 불러오지 못하거나 명세가 깨지면 원본 JSON과 오류가 남는다.

````markdown
```vega-lite
{
  "$schema": "https://vega.github.io/schema/vega-lite/v5.json",
  "description": "동시 요청 수가 늘 때 대기 시간이 어떻게 증가하는지",
  "width": "container",
  "height": 280,
  "data": {"values": [
    {"requests": 1, "latency": 18},
    {"requests": 4, "latency": 31},
    {"requests": 8, "latency": 67}
  ]},
  "mark": {"type": "line", "point": true},
  "encoding": {
    "x": {"field": "requests", "type": "quantitative", "title": "동시 요청 수"},
    "y": {"field": "latency", "type": "quantitative", "title": "대기 시간(ms)"}
  }
}
```
````

- 한 차트는 질문 하나에 답한다. 서로 다른 질문은 차트를 나눈다.
- 데이터는 명세의 `data.values`에 넣어 로컬 `file://` 플레이어에서도 재현되게 한다. 외부 URL을 런타임 입력으로 두지 않는다.
- 축 제목·단위·범례·`description`을 생략하지 않는다. 3D·장식적 효과·의미 없는 색을 쓰지 않는다.
- 본문 폭에 맞추려면 기본적으로 `"width": "container"`를 쓴다. 모바일에서도 라벨이 잘리는지 확인한다.
- 낭독에서는 차트를 `@fig`로 대응시키고, 축이 무엇인지 → 어디서 패턴이 바뀌는지 → 그 변화가 왜 생기는지 순서로 짚는다.

## 4. Mermaid 문법 함정 — 깨진 다이어그램을 만들지 않는다

Mermaid 파손의 대부분은 아래 몇 가지에서 온다. 하나라도 어기면 다이어그램 전체가 렌더되지 않는다.

- **특수문자가 든 노드 라벨은 큰따옴표로 감싼다.** 괄호·콜론·쉼표·대괄호·앰퍼샌드, 그리고 `/`·`\`·`(`·`{`로 *시작하는* 라벨은 감싸지 않으면 도형 문법으로 해석돼 파서가 깨진다.
  ```
  A[handleRequest(ctx)]      %% 깨짐 — 괄호가 도형 문법과 충돌
  A["handleRequest(ctx)"]    %% 올바름
  ```
- **여러 줄 라벨은 `<br/>`로 줄바꿈한다.** `\n`은 줄바꿈이 아니라 글자 그대로 렌더된다: `A["백엔드<br/>/api + /worker"]`.
- **노드 ID는 영숫자만.** 공백·문장부호 없는 단순 ID를 쓰고, 읽히는 이름은 라벨에 담는다: `userSvc["User Service"]`.
- **시퀀스 다이어그램 메시지는 평문으로.** `:` 뒤의 메시지에는 따옴표 이스케이프가 없어서 중괄호 `{}`·대괄호 `[]`·꺾쇠 `<>`·`&`가 들어가면 조용히 전체가 깨진다. 코드가 아니라 사람 말로 쓴다 — `A->>B: web_search({q: [...]})`가 아니라 `A->>B: web_search 호출(질의 목록 전달)`.
- **`stateDiagram-v2` 전이 라벨은 까다롭다.** `<br/>`(파스 오류)·괄호·여분의 콜론을 못 받는다. 여러 줄 라벨이나 특수문자가 필요한 상태 전이는 `flowchart`로 그리는 편이 안전하다.
- **엣지 라벨 안에 큰따옴표·파이프를 넣지 않는다.** 파이프가 라벨 구분자다 — 리터럴 `|`가 필요하면 `#124;`를 쓰거나 문장을 바꾼다.
- **타입 간 문법을 섞지 않는다.** `-->`는 흐름도용(시퀀스는 `->>`), `:::클래스`는 흐름도용(ER에는 없음)이다.

## 5. 가독성 — 읽히는 다이어그램의 구조

- **방향은 기본 `TD`(위→아래).** `LR`은 노드가 많아지면 가로로 퍼져 전체가 축소되고 글자가 안 읽힌다. `LR`은 **분기 없는 3~4노드 선형 흐름**에만 쓴다. 한 줄을 넘거나 분기가 하나라도 있으면 `TD`.
- **다이어그램 하나에 노드 10~12개까지.** 그 이상은 줌이 있어도 가독성이 무너진다. 이것은 문서 전체의 시각 수를 줄이라는 뜻이 아니라 **여러 부분 다이어그램으로 나누라는 신호**다. 관련 노드는 `subgraph`로 묶어 시각적 층을 만든다.
- **15개 이상이면 쪼갠다(하이브리드).** 전부를 한 장에 욱여넣지 않는다 — 모듈 관계만 담은 5~8노드 **개요 다이어그램** 하나를 먼저 주고, 각 부분의 세부는 본문 서술·표, 또는 해당 섹션의 **부분 다이어그램**으로 푼다. 학습 문서는 어차피 섹션 단위로 전개되므로, 세부 다이어그램을 그 세부를 설명하는 섹션 곁에 두면 자연스럽다.
- **화살표 스타일로 의미를 구분한다** (흐름도): `-->` 기본 흐름 · `-.->` 선택적/비동기/폴백 · `==>` 핵심 경로 강조 · `--x` 거부/차단 · `-->|라벨|` 분기 조건.

## 6. 색 — classDef 규칙 (플레이어 팔레트에 맞춘다)

의미 구분(성공/실패, 강조/후퇴, 전/후)은 `classDef`로 준다. 규칙 두 가지:

- **`color:`(글자색)는 지정하지 않는다.** 글자색은 플레이어 테마가 준다 — 하드코딩하면 테마와 어긋난다.
- **채움은 반투명(8자리 hex)으로.** 불투명한 밝은 채움은 종이색 배경과 따로 논다. 반투명은 배경 위에 자연스럽게 얹힌다(은은하게 `20`~`44`, 도드라지게 `55`~`77` 알파).

플레이어의 종이 팔레트와 어울리는 권장 세트 — 그대로 쓰면 문서마다 색이 들쭉날쭉해지지 않는다:

```
classDef hot  fill:#b3541b26,stroke:#b3541b,stroke-width:2px   %% 강조·지금 설명하는 곳
classDef ok   fill:#3e7c4f22,stroke:#3e7c4f                    %% 성공·정상 경로
classDef bad  fill:#b0323222,stroke:#b03232                    %% 실패·거부 경로
classDef dim  fill:#8b817315,stroke:#8b817366                  %% 배경·이번 논점 아님
```

색은 의미를 나를 때만 쓴다 — 구분할 것이 없는 다이어그램에 색을 뿌리지 않는다.

## 7. 직접 그린 SVG

Mermaid가 못 그리는 **커스텀 배치·정밀한 공간 의미**(메모리 레이아웃, 타임라인 위의 겹침, 기하학적 구조)일 때만 손 SVG로 간다. 그럴 때:

- `viewBox`를 지정하고 루트에 고정 `width`/`height`를 박지 않는다 — 플레이어가 `max-width:100%`로 맞춘다.
- 팔레트는 문서 테마와 맞춘다: 종이 `#fffdf9` · 잉크 `#221f1a` · 강조 `#b3541b` · 보조선 `#e8dfcd` · 흐린 글자 `#8b8173`. 위 classDef의 ok/bad 색도 그대로 쓸 수 있다.
- 글자는 **player.html에서 실제로 축소되어 보이는 크기**를 기준으로 14px 상당보다 작아지지 않게 한다. 원본 SVG 좌표계의 글자 크기만 보고 판정하지 않는다. 요소가 겹치지 않게 하고, **그리다 지저분해지면 여러 SVG로 나누거나 Mermaid·표로 회귀한다** — 조잡한 SVG는 깔끔한 텍스트만 못하다.
- `assets/`에 두고 상대경로로 임베드, 대체 텍스트에 요지 한 줄(`explanation-principles.md`).

## 8. 내보내기 전 30초 점검

다이어그램이 든 문서를 닫기 전에 훑는다:

1. 괄호·콜론 등 특수문자가 든 라벨을 전부 따옴표로 감쌌는가. 줄바꿈은 `<br/>`인가.
2. 시퀀스 메시지에 중괄호·대괄호·`&`가 없는가.
3. 노드가 12개를 넘지 않는가 — 넘으면 subgraph로 묶었거나 쪼갰는가.
4. 분기 있는 다이어그램이 `TD`인가.
5. classDef에 `color:`가 없고 채움이 반투명인가.
6. 이 한 장이 서로 다른 학습 역할을 둘 이상 떠안고 있지 않은가 — 그렇다면 여러 장으로 나눴는가.
7. 문서의 다른 시각과 정보가 겹친다면 시점·강조·배치된 학습 순간 중 하나가 달라 동반 시각으로서 별도 역할을 수행하는가. 아무 역할 차이 없는 복제만 제거한다.
8. 수식이 일반 텍스트로 남지 않고 KaTeX로 렌더되는가. 선언형 차트는 모든 축·단위·범례가 읽히며 오류 카드가 없는가.
9. 시간·상태·이동, 구조·관계, 입력-결과 변화에 해당하는 A등급 기회를 모두 시각화했는가.
10. 주요 H2가 4개 이상인데 그래픽 시각이 3개 미만이거나, 대표 그림 하나가 문서 전체 시각 역할을 떠안고 있지 않은가.
