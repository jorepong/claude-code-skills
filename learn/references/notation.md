# 표기 체계 — 번호가 무엇을 가리키는지 글리프로 구분한다

학습 문서에는 성격이 다른 네 가지 번호가 등장한다. **글리프(번호의 모양)만 보고 어느 좌표계인지 즉시 알 수 있도록**, 각 좌표계에 서로 다른 표기를 배정한다. 같은 모양의 번호를 두 좌표계에 겹쳐 쓰지 않는다.

| 좌표계 | 표기 | 가리키는 대상 | 범위 |
|---|---|---|---|
| **개요 학습 포인트** | 개념 `[N]` · 선행 `[P1]` · 구현 유닛 `[U1]` | `overview.md`의 개념 포인트·선행 학습·구현 유닛 | 개요 ↔ 개념/유닛 |
| **형제 문서** | `〈NN 제목〉` | 같은 개념 폴더의 다른 문서(파일 번호 NN) | 개념 폴더 |
| **코드 앵커** | `❶ ❷ ❸` (꽉 찬 동그라미) | 코드 블록 안의 특정 줄 | 한 문서 안 |
| **문서 내 섹션** | 번호 없는 서술형 `##` 제목 | 한 문서 안의 파트 | 한 문서 안 |

## 규칙

### 모든 코드 블록에 출처 성격을 표시한다 — 펜스 정보 문자열로

소스 코드·설정·셸 명령·쿼리·의사코드 블록은 **코드 펜스의 정보 문자열**(```` ``` ```` 뒤)에 출처 성격을 적는다. 본문 문단으로 라벨을 쓰지 않는다. 독자가 코드만 보고 실제 프로젝트에 존재하는지 추측하게 하지 않되, 그 표시가 본문을 차지하거나 낭독되지도 않게 하기 위해서다. 플레이어가 이 정보를 읽어 코드 카드 우상단에 작은 배지로 표시하므로, 문서에서는 펜스 한 줄로 끝난다. Mermaid·Vega-Lite처럼 플레이어가 시각 자료로 렌더하는 펜스와 단순 아스키 도식은 이 규칙의 대상이 아니다.

언어 이름 다음에 아래 키워드 하나를 둔다. 경로가 필요한 종류는 `키=경로` 형태로 쓰고, 확인할 수 있으면 `:시작줄`을 붙인다.

````markdown
```java file=src/main/java/com/example/TokenService.java:42
```yaml file=config/application.yml:18
```python example
```python ref=mastery/reference-impl/src/token_bucket.py:18
```pseudo
```java adapted=src/main/java/com/example/Foo.java:42
```bash cmd
```bash file=scripts/build.sh:1
````

| 키워드 | 뜻 | 플레이어 배지 |
|---|---|---|
| `file=<경로>` | 현재 프로젝트나 학습 자료의 **실제 파일**에서 그대로 가져온 코드·설정·데이터 발췌. 프로젝트 루트 기준 상대 경로, 프로젝트 기준이 없을 때만 절대 경로 | 경로 |
| `example` | 설명을 위해 새로 만든 코드로 **실제 파일에 존재하지 않는다.** 실행 가능 여부와 무관 | `예제 · 실제 파일 아님` |
| `ref=<경로>` | learn이 `mastery/reference-impl/`에 실제로 생성한 **참조 구현** 파일 | `참조 구현 · 경로` |
| `pseudo` (언어 자리에) | 문법적으로 실행되는 코드가 아니라 절차만 표현하는 **의사코드**. 언어 이름을 붙여 실제 코드처럼 보이게 하지 않는다 | `의사코드 · 실행 코드 아님` |
| `adapted=<원본 경로>` | 실제 파일을 단순화·재배열·조합했거나 일부 이름·값을 바꾼 **축약 예제**. `file`로 표시하지 않는다 | `축약 예제 · 원본 경로 과 다름` |
| `cmd` | 사용법을 보여 주려고 만든 **실행 명령 예제**. 실제 저장소의 스크립트를 그대로 인용했다면 `cmd` 대신 `file=`을 쓴다 | `명령 예제 · 실제 스크립트 아님` |

- 키워드가 없는 코드 펜스는 출처 미표시다. 모든 소스 코드·설정·명령·의사코드 펜스는 위 키워드 중 하나를 가져야 한다(초안 뒤 코드 출처 감사의 대상).
- 여러 실제 파일에서 가져온 코드라면 한 블록에 섞지 않는다. 파일별로 블록을 나누고 각 펜스에 경로를 쓴다.
- `file=` 블록에는 학습 문서용 코드 앵커 주석을 추가할 수 있다. 앵커 외에 코드를 단순화하거나 바꿨다면 `adapted=`로 내려 표시한다.
- 출처를 본문 문장에서 다시 설명하지 않는다. 독자가 알아야 할 것은 배지로 충분하고, 예외는 그 블록이 실제 파일인지 여부가 설명의 논점일 때뿐이다.
- 낭독 스크립트는 이 출처를 위한 문단을 만들지 않는다(`narration.md`). 펜스 정보 문자열은 문서 블록이 아니므로 1:1 정렬에도 영향이 없다.

1. **꽉 찬 동그라미 `❶ ❷ ❸`는 코드 앵커 전용이다.** 코드 블록 안 줄 끝에 달고(`// ❶ 헤더에서 토큰 떼기`), 본문에서 그 줄을 가리킬 때만 같은 번호로 참조한다(`❶의 resolveToken은…`). **섹션 제목·다른 문서·개요 포인트를 가리키는 데는 절대 쓰지 않는다.** 그래서 본문에서 동그라미를 만나면 독자는 망설임 없이 "근처 코드 블록의 그 줄"로 읽는다. (생략 없는 단정: 동그라미면 코드 줄이다.)

2. **한 문서 안에서 코드 앵커는 코드 블록을 가로질러 하나의 연속 번호다.** 블록이 여러 개여도 ❶부터 이어서 매기고(다음 블록은 ❼…), 블록마다 1로 되돌리지 않는다. 그래야 본문의 `❺`가 그 문서 안에서 단 한 줄만 가리킨다. 앵커는 문서 안에서만 유효하므로, 다른 문서의 코드 줄을 가리켜야 하면 먼저 그 문서를 `〈NN 제목〉`으로 참조한 뒤 그 안의 앵커를 말한다.

3. **다른 문서는 `〈NN 제목〉`으로 참조한다.** NN은 그 문서의 파일 번호(`02`, `04`), 제목은 짧게 단다 — 예: `다음 〈04 401 경계〉에서`, `앞 〈02 발급〉에서`. 동그라미로 다른 문서를 가리키지 않는다. 이 표기는 그대로 파일을 열 수 있는 좌표다.

4. **문서 내 섹션 제목에는 번호를 붙이지 않는다.** `##` 제목을 표준 용어와 실제 설명 대상으로 문자 그대로 단다(`## doFilterInternal이 요청마다 실행되는 조건`). 은유적 제목(`매 요청을 가로채는 문지기`)이나 함축된 제목을 쓰지 않는다. 섹션 순서는 마크다운 제목 위계로 드러나므로 번호가 필요 없다.

5. **개요 학습 포인트는 `[N]`·`[P1]`·`[U N]`으로 참조한다**(대괄호). 개념은 `[N]`, 선행은 `[P1]`, 구현 유닛은 `[U1]`처럼 쓴다. 이미 다른 세 좌표계와 모양이 달라 혼동되지 않으니 그대로 둔다.

**문서 H1 제목 형식**: `# [개요포인트] 개념명 · NN 섹션제목`. 예: `# [6] 인증 흐름 조립 · 03 검증·주입`. `[6]`은 개요의 학습 포인트 번호, `03`은 이 문서의 파일 번호(`03-….md`와 일치), 그 뒤는 서술형 섹션 제목이다. 제목에 동그라미를 쓰지 않는다. (개요 없이 진행하는 '가볍게' 모드에서는 개요포인트 대괄호를 생략하고 `# 개념명 · NN 섹션제목`으로 둔다.)

> **왜 이렇게 나누나.** 이전에는 같은 `❶ ❷ ❸`가 코드 줄·문서 내 파트·형제 문서를 동시에 가리켜, 본문의 `❹`가 "위 코드의 ❹ 줄"인지 "문서 04"인지 구분되지 않았다. 좌표계마다 글리프를 달리하면 번호의 *모양*이 곧 그 답이 된다 — 동그라미면 코드 줄, `〈NN〉`이면 다른 문서, `[N]`이면 개요. (본문에서 "첫째·둘째"식 일반 열거가 필요하면 `①②` 같은 빈 동그라미가 아니라 말로 풀거나 `(1)(2)`를 쓴다. 꽉 찬 동그라미는 코드 앵커로 예약돼 있기 때문이다.)

원본 코드나 참조 구현 파일은 수정하지 않는다. 코드 앵커는 생성되는 학습 문서 안에만 단다.
